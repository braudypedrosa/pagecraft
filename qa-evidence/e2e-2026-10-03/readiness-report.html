Pagecraft · build 90723a6 on staging · 3 October 2026

Readiness Review

A full end-to-end pass over every feature and role, plus a risk-first code review of the whole codebase with each finding checked against the code before it was listed.

Update · 5 October 2026: fixes deployed to staging

Staging now runs 58555d8. It fixes every verified finding except the shared database, which is intentional. Production still runs cc026d6. The gateway (v23) is shared with production and was checked for compatibility before deploying.

Fixed and checked:

  • All 1,607 tests pass, and all 24 UI gallery baselines match.
  • Spoofed IP headers no longer bypass rate limits.
  • The published home page is 81 KB instead of 397 KB, and loads in 2.2 s instead of 26 s.
  • The sitemap, a styled 404 page and old-slug redirects work.
  • Failed form posts no longer count toward the inbox cap.
  • Dates show in the reader's own time zone.
  • The review stores migrated to one file per record.
  • The editor runs under the new canvas script policy.

Still open:

  • Signed-in latency is still 1–2.6 s; fixing it needs a hosting decision.
  • Three follow-ups need a database migration: an accept step for library shares, the WordPress site URL in the credentials list, and token reuse detection.
  • Owner invites still take effect without the person accepting.
  • Schedules still run on a 5-minute cron.

Each finding below has its status.

As reviewed on 3 October: not ready for production

The product works: 71 of 90 end-to-end checks pass, and every permission boundary held under test. What blocks launch is a short list of problems that would hurt real customers:

  • A content editor can run script in the owner's editor.
  • Staging and production share a database that staging can write to.
  • Rate limits trust a header any client can set.
  • Several stores lose data once more than one server process runs.
  • Two editor paths destroy content.
  • Published pages take 15–31 seconds to load fully.

H1Security

Fixed Fixed. CMS text in rich slots is escaped and rich fields go through an allowlist.

A content editor can run script in the owner's editor

A CMS text field bound to a Text widget's rich-text slot is inserted as raw HTML. The auto-mapper makes that binding by default when a collection has no rich field. The server accepts any text in a text field, and the editor canvas is same-origin with no CSP, so the script runs with the owner's session. On the published site it is a visitor-facing XSS.

Where
core index.ts:4209, 4277, 4414, 7258 · content.ts:154, 215 · cms-validation.ts:170
Fix
Escape field-bound values unless the field is rich text, limit rich slots to rich fields, and sanitize rich output at render.

H3Security

Fixed Fixed and verified on staging: spoofed headers no longer escape the limit.

Anyone can spoof their IP, defeating every rate limit

Both domains resolve straight to the origin (67.223.118.197, LiteSpeed) with no Cloudflare in front, yet the server trusts the client's cf-connecting-ip and X-Forwarded-For headers. Per-source limits on sign-in, forms, registration and clicks can be bypassed. Flooding fake sources fills the 5,000-key throttle maps, which then refuse every new real visitor.

Where
app.ts:379-381 · mail.ts throttle().take · checked live 3 Oct
Fix
Use the socket peer address (or the hop LiteSpeed appends); trust CF headers only from Cloudflare ranges; evict the oldest key instead of refusing.
Found by
review, verified

H5Forms

Fixed Fixed and verified: failed posts are kept separately (200 max) and don’t count toward the cap.

Failed submissions can fill a site's inbox and block real ones

Validation failures are stored as entries, and the inbox refuses everything once 10,000 entries exist. Anonymous POSTs missing a required field can fill it in under 2 hours (faster with H3). After that every real submission gets a 503, and recovery is one delete at a time.

Where
submissions-routes.ts:125-130 · submissions.ts:102
Fix
Don't store failures (log a count instead), or exclude them from the cap.

H6Data loss

Fixed Fixed and verified: one file per record; the migration ran on staging.

Reviews and live-review links lose data across server processes

Each process reads the state file once and rewrites its whole in-memory copy on every change, so one process overwrites another's assignments, comments and decisions, and a revoked review link comes back active. Today each app runs one Node process, but LiteSpeed starts more under load, and a leftover deploy process is running against the same files (H11).

Where
reviews.ts:295-318 · live-reviews.ts:21-40
Fix
One file per record (as schedules and assistants already do), or lock and re-read on every write.
Found by
